# 语言与国际化（i18n）规范（N2）

对应设计评审 N2「多国时区/货币/语言与夏令时处理规范」的语言维度。
时区与夏令时见 `time.md`，货币与汇率见 ADR-0014/ADR-0019。本文回答一个问题：
**系统里每个位置的"语言"由谁定、怎么保证稳定。**

## 1. 现状基线（2026-11-12 核对）

| 位置 | 现状 | 性质 |
|---|---|---|
| API 契约（`contracts/openapi.yaml`） | 字段名全英文 snake_case | 稳定键，冻结于契约门禁 |
| 枚举值（`FEASIBLE`/`P0`/`GROUND`…） | 全英文 SCREAMING_CASE | 稳定键，冻结于契约门禁 |
| API 错误（`app/api/errors.py`） | `error.code` 英文稳定键 + `message` 中文 | **code 是机器键，message 是给人看的** |
| iOS 客户端 | 中文单语；无 `.strings`/`.xcstrings` | 不做假国际化（未排期就不建骨架） |
| LLM 产出（纪要/助手回复/解释） | 中文（系统 prompt 中文，见 `app/llm/prompts.py`） | prompt 版本化，语言随版本记录 |
| 数据面（地名/客户名/公司名） | 用户输入原文存储，不翻译不规范化 | 事实原样保留 |

## 2. 分层规则

### 数据面：原文即真相

地名、客户名、公司名、纪要原文**按用户输入原文存储**。系统不做翻译、不做
编码规范化（全角/半角）、不猜语言。理由：这些字段是业务事实（发票、合同、
CRM 回写都要用），任何"顺手翻译"都是数据篡改。展示层要怎么本地化是客户端
自己的事。

### 契约面：英文稳定键，中文永不进协议

`error.code`、枚举值、字段名、`unplaced_reason`、`data_gaps` 标签等一律英文
稳定键。**任何面向机器的字符串都不允许出现中文**——客户端按稳定键渲染本地
文案。`error.message` 是唯一的例外（给人看的即时提示，当前中文）；客户端对
`code` 做映射渲染，`message` 仅作兜底展示。

### 解释面：LLM 产出中文，语言是 prompt 版本的一部分

纪要、助手回复、计划解释、复盘摘要等 LLM 产出当前为中文。语言策略写进系统
prompt（模板已如此），prompt 版本号随产出一起落 `llm_invocations`——因此
"这条产出的语言"可由 prompt 版本追溯。未来若需要英文产出，**新增 prompt
版本**（如 `v2-en`），不原地改写；模板降级文案同样保持中文并与在线版本同语义。

### 客户端面：MVP 中文单语，不建假 i18n

iOS 首发中文单语。**没有排期就不创建空 `.strings`/`.xcstrings` 骨架**——
半吊子本地化比没有更糟（让人误以为已支持）。引入多语言时的路径：
String Catalog + 以契约稳定键为 key 的映射表 + 每语言截图验收进 `make ios-test`。

## 3. 与其他规范的正交性

- **时区/夏令时**（`time.md`）：墙上时间按 `timezone_home` 日历切分，与语言无关；
  日期/时刻的**展示格式**属客户端，服务端契约只传 ISO 8601。
- **货币**（ADR-0014/0019）：金额永远带 `currency` 原码（ISO 4217），不做币种
  名称本地化，不假折算。
- **排序/搜索**：客户与地点名的检索按原文前缀匹配；中文分词/拼音检索属未来
  增强，不进 MVP。

## 4. 范围外（显式不做）

- 自动翻译任何用户数据；
- 多语言 UI（未排期）；
- 服务端按 `Accept-Language` 切换 `message` 文案（`code` 已足够客户端本地化）；
- LLM 产出多语言并行版本（单租户单一语言偏好，出现真实需求时走新 prompt 版本）。
