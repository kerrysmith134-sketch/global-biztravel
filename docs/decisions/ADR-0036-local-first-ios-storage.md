# ADR-0036：iOS 本地优先存储与票据证据仓

- 状态：已接受
- 日期：2026-11-25

## 背景

Global Business Travel OS 的 iOS 客户端必须支持本机优先的行程与差旅记录，同时允许云端模式在网络可用时同步。费用和报销涉及原始票据，不能把一个客户端字符串引用误认为原件已持久化，也不能在本地文件丢失或损坏后继续生成看似完整的报销证据。

本地存储与服务端 PostgreSQL 具有不同的运行约束：客户端采用 SQLite document 表和 Codable 载荷；原始票据二进制则应留在应用私有文件目录，避免把大文件或敏感原件直接放入 SQLite。

## 决策

1. **SQLite document 表结构**：业务表使用真实存在的查询标量列（如 id、外键、状态、时间）与完整 Codable payload。通用 document upsert 仅用于具有 payload 列的表；索引/去重表（如 `proactive_triggers`）必须使用符合其实际 schema 的 SQL，不得伪造 payload 列。
2. **部分更新语义**：本地 upsert 在事务内先按主键执行 UPDATE，只更新调用方明确提供的标量列及 payload；不存在时才 INSERT。新行仍必须满足表的全部 NOT NULL 约束。禁止通过向不存在的列写值来模拟服务端字段。
3. **事务语义**：最外层事务使用 `BEGIN IMMEDIATE`；嵌套事务使用 SQLite SAVEPOINT。嵌套失败只回滚当前 savepoint，即使调用方捕获异常，失败层的变更也不得泄漏到外层提交。多表业务闭环必须把事实记录与状态变更放入同一事务。
4. **票据原件**：ReceiptVault 将原始字节保存在应用私有目录，SQLite 只保存不透明 storage key、SHA-256、字节数、MIME、原始文件名、行程归属和上传状态。文件名不得用于构造路径；不得向 UI 或 API 暴露私有 storage key。
5. **票据可信度**：费用只能关联当前行程拥有的 Receipt Asset。引用票据时必须能读取原件并验证 SHA-256；云端模式只有收到服务端确认的 Asset ID 后才可把票据当作云端资产。LOCAL_ONLY/PENDING_UPLOAD 不等于服务端已保存。
6. **报销证据快照**：创建 ExpenseReport 时固定每笔费用的票据 Asset ID、SHA-256、原始文件名、MIME 和字节数。引用的原件不存在、跨行程或哈希不匹配时，本地报销快照创建必须失败，不得产生部分报销单。
7. **结账评估**：Closeout Readiness 是从已持久化行程、拜访、费用、票据和报销快照派生的只读模型；不得改写 Trip 计划版本或伪造拜访完成。阻塞项与提醒分开，多币种分别汇总，不使用估算汇率合并金额。
8. **主动式执行**：签证提醒的本地批准复用 LocalVisaService 的正式案件模型与状态机，并将案件创建和建议状态更新原子提交。触发登记、建议记录必须遵守各自表 schema，并在同一事务内提交。

## 后果

- UPDATE-first upsert 消除了局部状态更新因 INSERT NOT NULL 检查而失败的问题，同时保留新行完整性约束。
- SAVEPOINT 使嵌套领域操作能够被安全捕获、回滚和恢复。
- ReceiptVault 可以离线保存原件，并在联网后按持久化状态上传；失败不会删除本机原件，也不会将上传标记为成功。
- 本地报销快照能保留服务端同等级别的票据证据元数据，并阻止无效原件进入报销证据链。
- OCR 候选的客户端人工审阅、对象存储孤儿对账及完整真实后端 UI 运行仍按 H2.13 验收清单单独验证；本 ADR 不宣称这些未完成工作已经落地。
