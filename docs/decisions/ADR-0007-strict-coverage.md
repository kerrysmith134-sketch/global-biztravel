# ADR-0007：成功解必须覆盖全部 eligible 停靠

- 状态：已接受（Accepted）
- 日期：2026-10-28
- 相关文件：`packages/planning-engine/travel_planner/pipeline.py`、`packages/planning-engine/tests/test_pipeline.py`
- 相关需求：设计文档 §6.4（覆盖不变量）、I1（可行性不由 LLM 宣布）

## 背景

端到端验收中发现：一次导入 8 个拜访的出行，求解器把 **全部 8 个** 停靠放入 `unplaced`，
但独立验证器仍判 `feasible=true`，Worker 照常落了一份 0 停靠的计划。这正是设计文档 §6.4
警告过的"静默错误"：计划看起来成功，实际什么都没排。

## 决策

在流水线的兜底链中增加**覆盖检查**：求解器返回后，取出已物化的 `days[].stops[].visit_id`，
若任一 `eligible` 停靠未被排入：

1. 记录失败原因，继续尝试兜底求解器；
2. 两个求解器都无法覆盖 ⇒ 抛 `SolverFailed`，任务终态失败，不落计划版本。

`unplaced` 列表从此只承载**预检阶段**剔除的停靠（缺坐标、容量、确定不可行的时间窗），
不再是"求解器没排进去"的垃圾桶。

## 后果

- 好处：不再产生"0 停靠但可行"的计划；用户看到的是明确的求解失败与原因。
- 代价：原本"部分成功"的场景（例如一个时间窗完全排不进）会整体失败，需要用户调整输入
  （如改为航空、放宽窗口）后重算。这是设计要求的语义：宁可不给，也不给假计划。
- 测试调整：原 `test_unreachable_window_degrades_but_stays_feasible` 等用例改为断言
  `SolverFailed`；容量预检用例改为把出发地放在被保留城市，以继续验证"预检剔除 + 剩余全排"。
