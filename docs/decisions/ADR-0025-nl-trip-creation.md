# ADR-0025：自然语言创建出差走"解析 → 提案卡 → 人确认"三步

- 状态：已接受（Accepted）
- 日期：2026-11-02
- 相关文件：`app/llm/prompts.py`（`trip_intake` v1、`trip_creation_intent`）、`app/llm/providers.py`（确定性解析）、`app/services/assistant_service.py`（提案与 `create_trip_draft` 动作）、iOS `AssistantView`
- 相关需求：PRD P0-2「对话与 Excel 导入——支持用户通过自然语言创建出差」

## 背景

PRD 要求用自然语言创建出差，同时明确"AI 不得擅自决定"。直接把模型解析结果落库有两个风险：
字段缺失时模型会编造日期/国家；对话误判（问状态 vs 建行程）会凭空造出行程。

## 决策

1. **意图判定与解析分离且都确定性**：`trip_creation_intent` 用固定关键词判"是否在请求创建"
   （"这趟行程需要我做什么"不命中）；`trip_intake` v1 prompt 只允许提取消息里**真实出现**的
   国家/天数/日期，本地 stub 同口径实现（`StubProvider._trip_intake`），缺就缺。
2. **信息不足 → 反问，不猜**：缺国家或缺天数/日期时，助手回复列出缺失项，不产生提案卡，
   不建任何行程；过期出发日同样要求用户改口（不自动顺延——那是编造）。
3. **提案卡是待确认动作**：字段齐全时产出 `TRIP_PROPOSAL` 卡片（含 name/countries/窗口），
   iOS 上是"创建出差草稿"按钮；点击调白名单动作 `create_trip_draft`，`subject_id` 为提案
   消息 id。
4. **服务端二次校验 + 幂等**：执行时重新解析载荷（不信任客户端回传）、复查日期顺序与未来性、
   复查国家为两位字母；同一提案只能创建一次（重复确认 4xx）；产出为 `DRAFT` 行程，
   **不对外预订**（PRD 边界），结果以 `ACTION_RESULT` 卡片回流。
5. 出发日缺省规则：用户只给天数时，起点取"明天"并**在回复文案里明示**，用户可改口。

## 后果

- 好处：创建链路全程可审计（`llm_invocations` + 消息卡 + 行程 owner）；误判与缺失信息都
  落在"反问"而不是脏数据；与既有会话内动作共用人审/幂等框架。
- 代价：只支持显式日期或天数的输入（"下月初"这类相对表达需后续接入日期推理）；行程草稿
  创建后仍需用户到行程页补客户与拜访（PRD P0-3/4 的自然续接）。
