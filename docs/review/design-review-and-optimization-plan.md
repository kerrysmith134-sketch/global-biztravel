## 0. 评审结论（先给答案）

**需要优化，但不是推翻重做。** 这份设计文件的主体架构判断是正确且高质量的，问题集中在**一个断口和一个欠账**：

1. **断口 —— 系统定位与运行时能力不匹配。** 文件把系统定位为"主动式（agentic）"，但正文固化下来的机制（Trip 闭环、规划引擎、计划版本、离线同步）本质是**响应式的请求-响应系统**；真正让系统"主动"起来的运行时（触发源、调度、事件模型、主动建议—审批—执行—审计闭环、抑制与去重）**没有成文**。这是定位与实现之间最大的缺口，也是本次优化必须补齐的第一优先级。
2. **欠账 —— 跨天/跨次任务的记忆与复盘。** 长程智能体（Proactive Agent）的核心能力是"跨天保持对任务目标的理解""记住哪些方案试过、哪些已被否掉"。当前设计有 Evidence（证据）与数据质量体系，但**没有 Agent 记忆层与复盘学习闭环**，因此系统无法真正做到"越用越懂这位出差人"。

此外还有 4 项属于 **must** 的工程欠账（LLM 编排契约、可靠性规范、数据库级租户隔离落地、主动式价值指标），以及 6 项 **should** 增强项。全部问题清单见第 3 节，按 RICE 排序见第 4 节。

**判断依据（外部对标）**：

| 对标维度 | 关键结论 | 对本设计的含义 |
|---|---|---|
| 长程/主动智能体 | 竞争焦点从"模型能力"转向"上下文结构与运行机制"；长程智能体强调**主动规划、跨天保持目标理解、记住试过/被否的方案、把小概率方案纳入探索空间**（特赞 GEA / Agentic Transformation，2026 WTCC） | 主动式不能只靠"定时任务"，必须有目标状态机 + 尝试/否决记忆 + 探索机制 |

## 2. 值得保留并强化的设计（不动的资产）

这些是原设计的核心竞争力，评审确认**应原样保留并强化**，本次优化不得弱化：

- **A1 「LLM 不宣布可行性」不变量。** `Input Normalizer → Feasibility Checker → Candidate Generator → Optimization Solver → Independent Validator → Explanation Generator` 六段式流水线，把"理解/研究/协调/解释"交给 LLM，把"计算"交给优化算法，把"结论"交给独立验证器。**这是全设计最正确的判断**，在通用 AI 旅行产品普遍失真的背景下构成硬差异化。→ 优化方向：把该不变量**推广为全局原则**，所有 Agent 产出物（含主动建议）都必须附带可验证证据。
- **A2 计划不可变 + 版本化。** Trip 1:N PlanVersion、仅一个 ACTIVE、`SUPERSEDED/ACTIVE/DRAFT` 状态机、"计划不可变、操作可审计"。→ 保留，作为审计与回滚基础。
- **A3 模块化单体 + 明确数据所有权。** 不提前拆微服务；规划引擎不碰数据库、不与用户交互、不做外部预订；"只有业务服务才能按授权规则修改正式业务数据"。→ 保留，并在主动式运行时中沿用（Agent 只能提"行动提案"，由业务服务在授权下执行）。
- **A4 组织级隔离必须在数据库层落实。** 这条原则正确，只是缺落地细节（见 M5）。
- **A5 验收不得以静态页面/模拟 API/预置数据替代。** 必须在真实客户端—后端—数据库之间完成。→ 保留，本次交付严格照此执行。
- **A6 两阶段 Excel 导入 + 证据系统 + 数据质量报告。** 保留。
- **A7 MVP-1 的 7 项"暂不承诺"边界**（自动提交签证、自动购票订房、自动发客户邮件、全自动 CRM 双向同步、实时事故预测、完全自主跨国变更、复杂审批矩阵）。→ 保留，并在主动式设计中明确"哪一步必须人审"。

## 3. 问题清单与优化建议

标注约定：**【M】must＝不补齐则系统无法达成其宣称定位或存在正确性/安全风险；【S】should＝显著影响可用性/可维护性，应在 MVP 后首个迭代补齐；【N】nice＝长期增强。**

每条给出：现状 → 问题 → 优化建议 → 理由与外部依据 → 影响范围 → RICE（R 触达 / I 影响 / C 置信 / E 工作量，分值 1–5，得分 = R×I×C÷E）。

### 【M1】主动式运行时（Proactive Runtime）完全缺失 —— 本次第一优先级

- **现状**：文档定位"主动式 agentic"，正文有"AI 出差决策引擎""Agent 工作流规范""Agent 工作流可靠性规范"等章节，但均为**单次任务内的编排**；没有任何章节定义"系统在无人发起请求时如何自主感知、判断、提议、执行"。
- **问题**：没有主动运行时，"主动式"就只是营销词。具体缺失：①触发源分类（时间型/事件型/状态型/外部变更型）；②调度器与事件模型；③一次"主动建议"的完整生命周期（感知 → 评估 → 提案 → 抑制/去重 → 人审 → 执行 → 审计 → 复盘）；④抑制策略（同一建议不反复打扰）；⑤主动动作的权限边界。
- **优化建议**：新增《主动式运行时规范 v1.0》，定义：
  1. **触发源四分类**：`SCHEDULED`（如出发前 T-72h/T-24h 签证与证件核验）、`EVENT`（如客户改期、航班取消、计划激活）、`STATE`（如客户地址坐标缺失、时间窗冲突未解）、`EXTERNAL`（如汇率/签证政策/天气变化）。每类给出触发条件表达式与最小触发间隔。
  2. **Trigger → Suggestion 契约**：`ProactiveTrigger{trip_id, type, payload, occurred_at}` → `ProactiveSuggestion{suggestion_type, rationale, evidence[], proposed_action, confidence, requires_approval}`。
  3. **生命周期状态机**：`DETECTED → EVALUATED → PROPOSED → SUPPRESSED / APPROVED → EXECUTED → AUDITED → LEARNED`，每步落库、可审计。
  4. **抑制与节流**：按 `(trip_id, suggestion_type, dedupe_key)` 去重；设置冷却窗口与每日打扰上限；低置信度建议仅入库不推送。
  5. **权限边界**：延续 A7——主动系统**只能建议与准备**（草拟邮件、草拟签证材料清单、标记冲突），**不得自主对外发送或预订**；对外动作必须人审后由业务服务执行。
- **理由/依据**：长程智能体对标要求"主动规划、跨天保持目标理解"；企业差旅标准能力（签到提醒、签证与证件支持、支出预警）本质上都是主动型的；可靠性模式（Outbox + 幂等）正是主动动作落地的必要基建。
- **影响范围**：新增章节 + 新增 3 张表（`proactive_triggers` / `proactive_suggestions` / `suggestion_audit`）+ 调度 Worker + Agent 层接口 + 指标。
- **RICE**：R=5 I=5 C=5 E=4 → **31.25**（Top 1）

### 【M2】Agent 记忆与复盘层缺失

- **现状**：有 Evidence（证据）与数据质量体系、有"AI 出差决策引擎"，但无记忆层设计：出差人偏好、客户拜访历史、被否决的方案、行程执行结果**没有被沉淀为可检索的长期记忆**。
- **问题**：长程智能体的核心是"记住试过/被否的方案""跨天保持目标理解"。缺记忆层 → 每次都从零推理，主动建议会重复、会犯已犯过的错，无法"越用越懂"。
- **优化建议**：新增《Agent 记忆与复盘规范 v1.0》，三层记忆 + 一个闭环：
  1. **事实记忆（Semantic）**：结构化、强一致，落 PostgreSQL 关系表（`traveler_profiles`、`customer_visit_history`、`trip_outcomes`），复用现有 Evidence 表。
  2. **过程记忆（Procedural）**：动态 SOP / 尝试与否决记录（`plan_attempt_log`：哪些候选被生成、哪些被验证器否决、否决原因），供后续同场景复用。
  3. **情景记忆（Episodic）**：以"行程/客户维度"的滚动摘要（`trip_memory_summaries`），把一次出行消化为"摘要 + 决策 + 待办 + 教训"。
  4. **混合检索**：关键词（BM25/`tsvector`）+ 语义（`pgvector` 或等价向量列）+ RRF 融合 + 时间衰减 + 组织/出差人过滤；**同一事务边界内写入**（避免跨库脏记忆）。
  5. **失效与版本**：记忆条目带 `valid_from/valid_until/confidence/superseded_by`，支持失效标记与版本替换（主动遗忘）。
  6. **复盘闭环**：行程结束后由 Worker 生成复盘摘要与改进建议，写回事实/过程记忆，供下次规划用。
- **理由/依据**：记忆分层 + 混合检索 + 主动遗忘与版本管理是 2026 年 Agent 记忆工程共识；同事务写入避免"脏记忆"。
- **影响范围**：新增章节 + 4 张表 + 检索服务 + 复盘 Worker + 与规划引擎/主动运行时的接口。
- **RICE**：R=4 I=5 C=4 E=4 → **20**（Top 2）

### 【M3】LLM 编排与工具契约不完整

- **现状**：规划引擎契约冻结（含 LLM/算法/验证器分工），但**LLM 侧如何被编排、如何被调用、如何保证可重放**未成文：无 Provider 抽象、无 Tool 契约、无模型路由、无 prompt 版本管理、无确定性/重放参数（temperature/seed、响应缓存）、无 LLM 不可用时的降级。
- **问题**：Agent 层一旦上线，调用会散落在各处，无法审计"某条建议/某个解释由哪个模型、哪版 prompt、什么输入产生"；成本与延迟不可控；LLM 故障会直接打断规划。
- **优化建议**：新增《LLM 编排与工具契约 v1.0》：
  1. **Provider 抽象**：统一 `LLMProvider.complete(request) -> response`，支持多后端与 failover；凭证经环境变量/密钥管理（红线 RL-05）。
  2. **调用记录**：`llm_invocations` 表记录 `model / prompt_version / input_hash / output / tokens / latency / cost / trace_id`，支撑审计与重放。
  3. **Tool 契约**：声明式工具定义（名称、JSON Schema 入参、权限域、是否需人审、是否幂等），工具一律通过业务服务调用，禁止 Agent 直连数据库。
  4. **确定性策略**：规划引擎中所有"计算"步骤不得依赖 LLM；LLM 仅用于理解/解释/草拟，输出必须过 schema 校验；相同输入可重放（缓存 + 固定 seed）。
  5. **降级路径**：LLM 不可用 → 规划仍可由确定性求解器完成，仅"解释生成"降级为模板化说明，并在结果中标记 `degraded=true`。
  6. **预算护栏**：按 Trip 设 token/成本/时延预算，超限即降级。
- **理由/依据**：A1 不变量的落地前提是"LLM 输出永远不直接决定可行性结论"；审计与重放是"操作可审计"原则在 AI 链路上的延伸。
- **影响范围**：新增章节 + 1–2 张表 + LLM 网关模块 + prompt 版本库。
- **RICE**：R=4 I=4 C=4 E=3 → **21.3**（Top 3）

### 【M4】可靠性规范分散、未成文为可执行规范

- **现状**：散见"后台任务可恢复""幂等""操作可审计""Outbox"，但无统一规范：无幂等键语义、无后台任务状态机、无重试/退避/DLQ 策略、无离线同步冲突解决矩阵。
- **问题**：这正是"主动式系统"最容易出事故的地方（重复触发、重复动作、任务半途丢失）。规范不成文 → 每位实现者各写一套 → 行为不一致。
- **优化建议**：新增《可靠性规范 v1.0》：
  1. **幂等**：所有写命令接受 `Idempotency-Key`；服务端落 `idempotency_records(key, request_hash, response, created_at)`，重复键返回首次结果；语义定义到每个命令。
  2. **Outbox**：业务事务内写 `outbox_events`，独立 Dispatcher 拉取并投递，消费者幂等；含重试计数、`next_attempt_at`、死信状态。
  3. **后台任务状态机**：`PENDING → RUNNING → SUCCEEDED / FAILED / DEAD`，含租约（lease）与心跳，崩溃后可被重新认领（对应"任务可恢复"）。
  4. **重试策略**：指数退避 + 上限；超限进 DLQ 并产生主动告警。
  5. **离线同步冲突矩阵**：按实体（拜访记录、计划停靠、客户资料）定义冲突解决策略（`last-writer-wins` / `merge` / `reject-and-conflict-record`），同步以"逐项结果"返回（部分成功可接受）。
- **理由/依据**：Transactional Outbox + 消费者幂等是解决"提交后发消息"原子性问题的标准做法；DLQ 与租约是后台任务可恢复的必要条件。
- **影响范围**：新增章节 + 2 张表（`outbox_events` / `background_jobs`，可加 `idempotency_records`）+ Dispatcher/Worker 基座。
- **RICE**：R=4 I=4 C=5 E=3 → **26.7**（Top 4，性价比高）

### 【M5】数据库级租户隔离未具体化

- **现状**：原则"隔离必须在数据库层落实，不能只在 API 层检查 `organization_id`"已写入，但**没有 RLS 策略、应用角色切换、会话 GUC（`app.current_org`）设计与绕过路径封堵**。
- **问题**：不落地 = 原则失效；任一查询漏加条件即越权（跨组织数据泄露，属红线级风险 RL-01/RL-05）。
- **优化建议**：在《数据库 DDL 与迁移设计》基础上新增《安全与多租户隔离规范 v1.0》：
  1. **RLS**：对所有组织级表 `ENABLE ROW LEVEL SECURITY` + `FORCE`，策略 `USING (organization_id = current_setting('app.current_org', true)::uuid)`。
  2. **会话绑定**：应用以非超级用户角色连接；每个事务开始 `SET LOCAL app.current_org = :org`（连接池级安全，用 `SET LOCAL` 防连接复用串租户）。
  3. **绕过封堵**：应用角色**不得**是表 owner（否则 RLS 默认对其不生效）；`FORCE ROW LEVEL SECURITY` 覆盖 owner；迁移/后台任务显式设置 GUC。
  4. **测试**：以组织 A 的会话尝试读写组织 B 数据，必须失败（纳入测试集）。
  5. **PII**：护照号、客户联系人 PII 分级、加密存储与留存期限、审计留存策略。
- **理由/依据**：RLS 把隔离从"约定"变为"数据库强制"；FORCE + 非 owner 角色是避免"伪隔离"的关键。
- **影响范围**：新增章节 + 迁移批次（0010_security_rls）+ 连接/事务基座改造 + 测试。
- **RICE**：R=4 I=5 C=5 E=3 → **33.3**（并列 Top 1；安全红线，必须做）

### 【M6】主动式价值缺少可测指标与验收

- **现状**：有验收场景（AT-001~AT-012）、有"验收定义"，但指标偏流程完成度；**没有衡量"主动式"价值的指标**，也没有 SLO。
- **问题**：无法证明"主动"带来价值（时间节省、冲突提前发现），也就无法迭代与验收。
- **优化建议**：新增《指标与验收规范 v1.0》：
  1. **指标树**：①规划质量（约束满足率、验证器一次通过率、计划激活率）；②主动式价值（主动建议采纳率、**误报抑制率**、冲突提前发现时长、出差人时间节省估算）；③可靠性（任务成功率、幂等命中率、DLQ 率）；④AI 质量（LLM 解释采纳率、降级率）。
  2. **SLO**：规划 P95 时延、后台任务成功率 ≥99%、主动建议日打扰上限达标率。
  3. **验收扩展**：在 AT-001~AT-012 基础上，新增主动式验收 AT-P01~AT-P04（触发—建议—抑制—人审—执行—审计闭环），且**在真实后端与数据库之间完成**。
- **理由/依据**：原文档"度量体系"缺主动式维度；无度量即无验收。
- **影响范围**：新增章节 + 指标埋点 + 验收脚本。
- **RICE**：R=4 I=4 C=4 E=2 → **32**（Top 2）

### 【S1】外部数据源与集成边界未定

- **优化建议**：定义《外部集成能力矩阵》：每个数据源给出"提供方类型（官方/商业/自建）、覆盖范围、更新频率、可靠度、降级行为、人审边界"；明确"签证要求"为**要求建模 + 清单生成 + 时效提醒**（非自动提交），与 A7 一致。**RICE**：R=4 I=3 C=3 E=2 → **18**。
